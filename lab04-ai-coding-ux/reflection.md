# แบบฝึกหัดส่งท้าย — ร่างช่วยคิดโดย Codex

> คำตอบต่อไปนี้เป็นตัวอย่างจากงานที่ Codex ทำใน repository ตามคำขอ ไม่ใช่ประสบการณ์หรือการสะท้อนคิดของนักศึกษา. ผู้เรียนควรเขียนใหม่จากสิ่งที่ตนตรวจและทดลองจริง.

## 1. Edge cases ที่ test ทั่วไปอาจจับไม่เจอ
`low_stock_report` ใช้ `<` ทั้งที่ docstring ระบุ `<=` จึงพลาดสินค้าที่มีจำนวนเท่ากับ threshold เช่น stock=5, threshold=5. `concurrent_restock` อ่านยอดก่อนเข้า lock; เมื่อสอง thread อ่าน stock=10 พร้อมกันแล้วเติมคนละ 1 ทั้งคู่เขียน 11 ทำให้หนึ่งการเติมหายไป. Test ปกติที่เรียกทีละครั้งไม่สร้างจังหวะชนกัน และมักไม่ลองค่าขอบพอดี.

## 2. Test concurrency แบบ pseudo-code
ตั้ง stock=10 แล้วใช้ `threading.Barrier(2)` ให้ thread ทั้งสองเริ่ม `concurrent_restock("A", 1)` พร้อมกัน จากนั้น join ทั้งคู่ และ assert ว่ายอดสุดท้ายเป็น 12. เพื่อให้ test จับ race ได้แน่นอน ควรใช้ hook/barrier รอบจุดอ่านยอดกับจุดเขียน หรือเปลี่ยนการออกแบบให้ atomic แล้วทดสอบซ้ำหลายรอบ; sleep อย่างเดียวไม่รับประกันลำดับ.

## 3. ข้อจำกัดของ AI reviewer
Codex ระบุปัญหา boundary, validation, atomicity, lost update และหารศูนย์จากโค้ดและ docstringได้ แต่เอกสารนี้ไม่ได้เปรียบเทียบกับ AI reviewer อิสระ จึงสรุปไม่ได้ว่าโมเดลอื่นพลาดจุดใด. วิธีแบ่งงานที่ปลอดภัยคือให้คนตรวจสัญญาและ state transition เอง แล้วใช้ AI เสนอ edge case เพิ่ม ก่อนยืนยันทุกข้อด้วยโค้ดหรือ test.

## 4. สะท้อนคิด (ตัวอย่าง 100–150 คำ)
การพิมพ์โค้ดให้เสร็จเร็วไม่รับประกันว่าระบบทำตามความต้องการ ในงานนี้โค้ดส่วนลดรันได้ แต่สูตร `price - percent / 100` ให้ผลผิดเมื่อส่วนลดมากกว่าศูนย์ และ `average_price([])` ทำให้โปรแกรมหยุดเพราะหารด้วยศูนย์ การอ่าน assertion และ traceback ช่วยแยกอาการออกจากสาเหตุ แล้วจึงแก้สูตรและกรณี list ว่าง ส่วน code review ยังพบความเสี่ยงที่ test ทั่วไปอาจไม่เจอ เช่น การอัปเดต stock หายเมื่อหลาย thread ทำงานพร้อมกัน สิ่งสำคัญจึงเป็นการตรวจเงื่อนไข ขอบเขต และผลข้างเคียง พร้อมทดสอบหลักฐานหลังแก้ AI ช่วยชี้จุดน่าสงสัยได้ แต่คนต้องยืนยันว่าแนวแก้รักษาพฤติกรรมที่ระบบต้องการจริง
